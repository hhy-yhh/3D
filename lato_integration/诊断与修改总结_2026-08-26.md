# TRELLIS + LATO 质量诊断与修改总结

> **日期：** 2026-08-26
> **目标：** 定位「生成网格碎片化 / 点面过多」的真正根因
> **结论：** 根因是 **spconv int32 上限 → voxel 被截断到 16384 → VAE 重建不出形状**，不是训练问题、不是代码 bug、不是 L0 问题

## 二、诊断发现（重要）

### 1. L0=0 是正常的，不是 bug

四组实验（连 GT coords + GT feats 基线）都是 L0=0。文档 Bug 26 的「GT 直通验证」其实也写了 `Level 0 = 0`（且结果「无裂隙、完美重建」）。**v14 把 L0=0 当根因是误读。**

### 2. 顶点数量不是问题

四组实验 L1（~56K）、L2（~320K）差异都在 ±10% 内。feats 是 GT 还是 SLat、coords 是 GT 还是 SS，对顶点数量几乎无影响。**v17 追「L2/L1 ≈ 1×」追错了目标。**

### 3. CD 全 ≈0.307，feats/coords 完全不重要

```
A: GT coords + GT feats     CD=0.3069
B: GT coords + SLat feats   CD=0.3069
C: SS coords + GT feats     CD=0.3078
D: SS coords + SLat feats   CD=0.3071
```

连「完美输入」A 组都是 0.307。四组唯一共同变量是 **16384 个 voxel**。

### 4. 根因：spconv int32 上限 → 截断

```
GT latent 全量 52416 voxel → VAE → 无裂隙、完美重建（文档 Bug 26）
GT latent 截断 16384 voxel → VAE → CD=0.307 碎片化（本次实验 A）
```

**16384 个 voxel 对 VAE 重建来说太少（只有全量的 1/3）。**

---

## 三、根因链

```
① SS Flow 只有 16³（64:1 压缩）→ StructureHead 产出糊的 occupancy
   （th>2.0 时 97969 voxel，GT 只有 ~5000，厚壳）

② spconv 2.3.8 的 int32 上限（N×C×4 < 2³¹）→ 逼着 --max_coords 16384 截断

③ VAE 拿 16384 voxel（1/3 的 latent）重建不出形状 → 碎片化 CD=0.307
```

**关键定性：当前质量差的直接原因是「voxel 数量被截断」，不是训练问题。** 训练（SLat MSE 0.2）是次优的，但被截断问题完全掩盖了——因为连「完美 feats」在 16384 voxel 下都是 0.307。

---

## 四、spconv 调查结论

- spconv **2.3.8** 只有 3 个算法：`Native` / `MaskImplicitGemm` / `MaskSplitImplicitGemm`，**没有 `NVRTC`**
- 报错 `matmul_split_Simt_f32f32f32` 说明已用 split 算法，仍走 Simt（int32 上限还在）
- 错误提示说的「fixed in spconv 2.2/2.3」**实际没兑现**，int32 上限绕不过
- **唯一轻量手段是 fp16**：元素字节 4→2，int32 上限翻倍，可喂 ~52K voxel

## 五、fp16 方案（进行中）

### 已做
- `experiment_coords_vs_feats.py` 加 `--vae_fp16` 开关（默认关，保留 fp32）
- 逻辑：`vae.half()` + 输入 feats `.half()`

### 遇到的坑
`vae.half()` 后报 dtype 冲突：`mat1 Float mat2 Half`（在 `latent_expander` 的 attention 处）

**根因：** `AbsolutePositionEmbedder.freqs`（`lato/modules/transformer/blocks.py:41`）是硬编码 fp32 的**普通属性**（非 `nn.Parameter`/`register_buffer`），`.half()` 不会转它，导致 pos_embedder 输出 fp32，和 fp16 的 attention 权重冲突。

### 待验证的方案（不改 LATO 库）
在自己的脚本里手动把 freqs 转 fp16：

```python
if opt.vae_fp16:
    vae = vae.half()
    for module in vae.modules():
        if hasattr(module, 'freqs') and isinstance(module.freqs, torch.Tensor):
            module.freqs = module.freqs.half()
    pipeline.models["lato_vae"] = vae
```

freqs 值范围 [1e-4, 1.0]，fp16 可表示，转后无溢出风险。若 VAE 里还有别的「普通属性硬编码 fp32」，重跑会再报，逐个加入循环即可。

## 八、追加修正 (2026-08-26 同日晚) — fp16/截断结论被推翻

> ⚠️ **2026-08-28 复核：本节结论错误，已被推翻。** 当时核对的是损坏的本地副本 `database_lato/lato_latents/`（服务器上该目录**不存在**），其 coords 恰为 Z=127 扁平、128²=16384 个点。服务器真实训练数据是 `lato_latents_v2`（coords 26K-68K，均 ~41K，含 52416）。修正详见文末「十一、2026-08-28 复核验证与修正」。

对 `database_lato/lato_latents/latents/lato_vae_16dim_128/*.npz` 逐文件核对后发现：

- **全部 234 个 GT latent 的 coords 都是 16384**（编码硬上限），数据集里**根本不存在「52416」**。本文档第二/三/五节的「GT 全量 52416 → 截断 16384 → 数量太少」前提**不成立**。
- 实验 A（GT 完美输入）在 16384 下 CD=0.307，恰恰说明**瓶颈不在 voxel 数量**。
- 结论修正：**fp16 方案无的放矢，弃用**。真正的瓶颈是「VAE 输入分布不匹配 + 顶点云→mesh 粗糙」。
- 新方案见 `TRELLIS_LATO_完整实现流程_v2.md` 的 **v18：用 LATO 完整 encoder/decoder 精化草稿 mesh**（Stage 2 走 LATO 原生 PointNet encode → decode 路径，绕开 16 维语义特征分布不匹配）。

## 九、真正根因 (2026-08-26 深夜)——CD 度量 bug + 三角汤

对 GT mesh 坐标逐文件核对发现：**GT mesh 是原始毫米单位（span ~350），decode 输出是归一化 [-0.5,0.5]（span ~1）**。旧 `compute_all_metrics` 把 pred 除以 GT 毫米对角线 → pred 缩成小点 → **CD 恒 ~0.27，与生成质量无关**。

- **已验证**：用真实 GT mesh + 完美重建（和 GT 同形状），旧方法得 **0.26 分**，新方法（各自归一化到单位）得 **0.000**。
- 修复后：A 组（GT 输入）0.0093、SS 生成路径 **0.0022**——**生成几何其实是正确的**。
- 视觉「碎片化 / 细小三角」来自 KDTree 建 mesh 三角汤（1790 万面），已用**格点四边形化（47 万面）+ Poisson 光滑重建**解决（Poisson 后 NC 0.46→0.66）。
- 结论修正：**v18 的「LATO 精化」解决的是不存在的问题**；真正的问题是 CD 度量 + 建 mesh，与架构/训练/生成能力无关。详见 `TRELLIS_LATO_完整实现流程_v2.md` 的 **v19**。

## 十、后续实验与结论 (2026-08-27)

### 观感问题
CD 修复后几何正确（0.002），但观感仍糙：grid 方块感/非流形（平滑炸尖刺）、Poisson 纸糊、Poisson+平滑 Hausdorff 0.10（薄特征被磨掉）。生成路径最终：CD 0.002、NC 0.66，表面糙。

### 服务器 latent 澄清
本地 GT latent 退化（全 Z=127 扁平）只是本地副本损坏；**服务器 latent 是正常 3D**，SLat 训练数据没问题，撤销「扁平污染」假设。

### 重训结论
- SS 32³：被阻塞（无 32³ SS encoder）。
- SLat 重训（不加数据）：MSE 0.2 已到「234 数据 + prompt 信息量」极限，降不下去。
- 可行：VAE 剪枝头微调（v17 方案，CD 修复后需重新评估）、LogitSharpener。

### 模块审计
管线大部分与流程图官方一致（CLIP / SS/SLat Flow / VoxelVAE / ConnectionHead）；唯一真偏差是自写 **LatoStructureHead**（替代 TRELLIS SparseStructureDecoder，16³→128³ 糊）。**没有模块不一致导致的连锁问题**。

详见 `TRELLIS_LATO_完整实现流程_v2.md` 的 **v20**。

## 十一、2026-08-28 复核验证与修正

> 逐项复核 v19/v20 的关键结论（服务器实测），修正 3 处错误。

### 1. ✅ 复核确认：v19「CD 度量 bug」正确

- **test 评估 GT 是毫米**：`test/metadata.csv` 的 `file_path` 指向 `/data/huanghaoyang/3D/database/`（原始毫米 mesh，如 `20250423_1800_838505.stl` 的 diag=432.5，即文档「355×212×126 mm」）。`meshes` 是 symlink → `meshes_normalized`（训练 mesh 归一化），但评估 GT 走 metadata `file_path`，不用 symlink。
- **旧度量精确复现 0.27**：真实 pred（归一化 diag≈1.1）+ 真实 test GT（毫米 diag≈432），旧度量（两者都除以 GT 对角线）→ **CD=0.2700**；新度量（各自居中+缩放到单位）→ **0.0022**。「旧 CD 恒 ~0.27」是纯度量假象，**生成几何正确**。
- 当前 grid 模式数字复现文档：**CD 0.0022 / HD 0.105 / NC 0.46**。

### 2. ❌ 修正第八节「全部 16384」—— fp16/数量问题重新打开

- 服务器上 `database_lato/lato_latents/` **不存在**；真实训练数据 `lato_latents_v2/latents/lato_vae_16dim_128/` 的 234 个文件 coords = **26,372 ~ 67,834（233 个不同值，均值 ~41K）**，包含 52416。
- §八 的「全部 16384」来自**损坏的本地副本**（Z=127 扁平 → 128²=16384 个点）。
- 推论修正：**fp16「喂更多 voxel」重新打开**；实验 A 用 `--max_coords 16384` 只喂了 GT latent（~40K）的一半，不是「完美输入」，据此断言的「数量不是瓶颈」**撤回**。

### 3. ⚠️ 修正厚壳数字（Bug 26「GT ~5000」）

- GT occupancy（`ss_occupancy_128_v2`）实测均值 **~38,577**（128³ 的 1.8%），非「~5000（0.24%）」。
- SS th=2.0 产出 97,969 = **2.5×** GT（非 20×）。厚壳真实但程度更轻。
- 推理不截断会 OOM（97,969 coords → VAE decode），当前用 `--max_coords 16384`（top-16384 by confidence）正常运行。
